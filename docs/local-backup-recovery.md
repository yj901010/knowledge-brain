# Local encrypted backup and isolated restore

This is the operator recovery procedure for the existing local k3d architecture.
It preserves the13 services, their database ownership, private Spaces, TLS,
Outbox/Connect-only publication and existing pinned images. It adds no application
dependency or distributed transaction. Runtime drill evidence is recorded separately
in `local-backup-recovery-validation.txt` after verification completes.

## Recovery boundary

`scripts/local_recovery.py` produces a consistent **cold** backup. Applications,
Keycloak/Registry, Connect and operators stop gracefully, then all persistent stores
stop before their files are copied. The source PVCs are never replaced or deleted.
Original replica counts and cluster UID are journaled before shutdown; normal errors
resume them in `finally`. After an interrupted process, `resume-source` uses that
journal and rejects a changed source UID. An OS file lock prevents concurrent source
backup/resume operations. No factory reset, prune, PVC deletion or service-boundary
change is part of recovery.

The bundle contains:

- all current local PVCs (13 with observability; the original drill covered7): complete PostgreSQL17 cluster including roles, Keycloak,
  Registry, service databases, Outbox, WAL and replication slots; Kafka broker and
  controller logs including Connect configuration/offset/status topics and consumer
  offsets; versioned MinIO objects; Cassandra, OpenSearch and ClickHouse projections;
- Kubernetes service configuration, TLS keys/CA and credentials, RBAC, network policy,
  Strimzi CRDs/resources, Kafka cluster/node IDs and Helm release records;
- the pinned running workload images, including independently built local images;
- source/contracts/charts/scripts, excluding `.git`, build/cache directories,
  `.local`, `work` and environment credential files.

Completed test Jobs, Pods and their owned ConfigMaps are not restored. Kubernetes
service-account tokens and `kube-root-ca.crt` are regenerated by the new cluster;
application TLS/signing keys and credentials are restored. Restore is **whole-environment**, same pinned software,
Linux/amd64; it is not selective entity recovery, version upgrade, online PITR or
zero-downtime HA. Physical backups restore projections with their matching offsets;
existing canonical rebuild paths remain authoritative for future selective rebuilds.

## Storage and keys

Every archive and the private manifest use AES-256-GCM with a fresh96-bit nonce,
full128-bit authentication tag and authenticated format header. The operator reuses
the already installed `cryptography==44.0.3`; no Python library enters Java images.
Data streams directly between containerd/PVC tar and encrypted host files. Decrypted
archives and credentials are not written to a host staging directory or general logs.
The small public `backup.json` contains only status, identity, byte counts and hashes.
`COMPLETE` is written atomically only after authenticating every archived byte.

Use a dedicated key directory: key generation restricts it and the key to the current
OS user. Keep the base64 recovery key separately from the bundle. Losing the key makes
the backup unusable. Copy both to separate trusted storage before considering this a
host-loss backup; this implementation does not silently upload private data to a
cloud account. The checked host-disk copy survives Docker/WSL factory reset but does
not protect against loss of that Windows disk. No off-host copy is claimed.

## Commands

From `C:\dev\knowledge-brain`, with Docker Linux/cgroup2 running and existing Python,
Docker, kubectl and k3d available:

```powershell
python .\scripts\local_recovery.py keygen `
  --key "$env:USERPROFILE\Documents\Codex\recovery-keys\knowledge-brain.key"

python .\scripts\local_recovery.py backup `
  --key "$env:USERPROFILE\Documents\Codex\recovery-keys\knowledge-brain.key" `
  --output "$env:USERPROFILE\Documents\Codex\backups\knowledge-brain\NEW-UNIQUE-BACKUP"

python .\scripts\local_recovery.py verify `
  --key "$env:USERPROFILE\Documents\Codex\recovery-keys\knowledge-brain.key" `
  --backup "$env:USERPROFILE\Documents\Codex\backups\knowledge-brain\NEW-UNIQUE-BACKUP"
```

Existing backup directories, in-progress blobs and keys are never overwritten. There
is no automatic retention deletion. Keep at least the last known-good verified bundle
and its key; create a new backup before significant data/configuration changes and at
the end of a development day. Scheduling is not installed implicitly. Recovery-point
exposure is time since the last completed backup, not zero; measured durations belong
to the small local drill dataset and are not a production RTO/RPO guarantee.

For interrupted backup:

```powershell
python .\scripts\local_recovery.py resume-source `
  --journal .\.local\recovery-runs\NEW-UNIQUE-BACKUP.json
```

The runtime bundle's source archive records the backup-time source. A separately
authenticated final recovery kit can preserve the subsequently tested operator
scripts and runbook without rewriting that immutable point-in-time bundle:

```powershell
python .\scripts\local_recovery.py export-kit --key C:\path\recovery.key `
  --output C:\path\recovery-kit.tar.gz.enc
python .\scripts\local_recovery.py unpack-source --key C:\path\recovery.key `
  --archive C:\path\recovery-kit.tar.gz.enc --destination C:\dev\NEW-RECOVERY-SOURCE
```

Extraction authenticates first, requires a new destination, rejects absolute paths,
parent traversal and links, and bounds extracted file count/size. Preserve a trusted
copy of the operator script and Python/cryptography prerequisites with the kit.

For a real restore, recover/extract the source kit on a machine with the same pinned
k3s/k3d prerequisites. Use an unused target name and API port. Restore authenticates
**all** files before creating any cluster and refuses an existing cluster. Source
context `k3d-knowledge-brain` is never accepted as a target.

```powershell
python .\scripts\local_recovery.py restore `
  --key "$env:USERPROFILE\Documents\Codex\recovery-keys\knowledge-brain.key" `
  --backup "$env:USERPROFILE\Documents\Codex\backups\knowledge-brain\NEW-UNIQUE-BACKUP" `
  --name knowledge-brain-restore-abc123 --api-port 6650 --k3d C:\path\to\k3d.exe
```

The new single-node local drill cluster has the same logical application/storage
architecture, separate Docker network, kubeconfig and Kubernetes UID. It restores
retained static PVCs only into new directories. Before applications run, every
restored volume's sorted per-file SHA256 inventory must match, and row counts and
ordered-row fingerprints of every non-system PostgreSQL table must match in each
database separately. Kafka cluster/node IDs, CA/user credentials, topic records and
offsets are preserved before operator reconciliation. Services retain their internal
addresses, including Cassandra's stable broadcast Service address. No source service
is repointed to the clone.

Source resumption explicitly wakes existing Strimzi PodSets after the operator
restarts and checks real broker/controller Pod readiness; an old Kafka Ready
condition alone is insufficient.

On the32GB local host, run one full application environment at a time. After the
source backup has resumed successfully, stop the source k3d cluster for the drill;
start it again after stopping the clone. Both clusters and their PVCs remain intact.
Port-forward processes end when their Pods stop: restart the existing Gateway/Login/
Headlamp forward scripts when returning to the source. Do not overwrite the source
kubeconfig with the clone's `.local/recovery-runs/*-kubeconfig.yaml`.

If configuration application fails after all captured volumes were copied, `restore
--resume` can continue that same frozen target only. It requires the original
journal, matching source/target UIDs and backup path, every original volume hash and
the exact restored PV/PVC bindings. It never rewrites volume data or reimports
images. Once stores have changed files or the target is RESTORED, resume refuses;
use a new target rather than overwriting a running environment.

## Functional recovery drill

`Run-LocalRecoveryValidation.py --mode prepare` creates one dedicated registered
account, a claimed private Space, Note v1/v2, Concept link, sealed binary and another
guest identity/Note. Its browser credentials move directly from the validation Pod
to a Kubernetes Secret, without printing them. That Secret is backed up encrypted.
Prepare **before** backup; do not recreate the fixture after restore.

Run `--mode verify --cluster knowledge-brain-restore-abc123 --kubeconfig PATH` in the
clone. The browser trusts the restored CA, performs a fresh password login to the
existing Keycloak account, reads the same IDs/history/link, downloads the old object
and compares SHA256, checks the old guest credential and private cross-Space denial,
then writes Note v3 and waits for the restored Outbox/Connect/Kafka/Activity path.
This validates original data plus post-restore continuity rather than only empty
process startup. Test traces/screenshots and credential dumps are not enabled.

Also verify all10 connector/tasks are RUNNING, all application workloads Ready and
existing Registry artifacts available. Record source and target UIDs, cold-backup
time, bytes, table/file counts, browser Job UID and post-return source health.

## Sources and compatibility

- [PostgreSQL17 filesystem backup](https://www.postgresql.org/docs/17/backup-file.html)
  requires server shutdown and a complete cluster including WAL.
- [Strimzi deployment/operator guidance](https://strimzi.io/docs/operators/latest/full/deploying.html)
  documents node-pool IDs and operator-managed resources.
- [Strimzi backup implementation](https://github.com/scholzj/strimzi-backup)
  restores paused Kafka resources and cluster identity before reconciliation; this
  project adds the matched persistent files and does not install that external tool.
- [Cryptography44.0.3](https://cryptography.io/en/44.0.3/hazmat/primitives/symmetric-encryption/)
  requires authentication finalization before decrypted bytes may be used. Restore
  authenticates the entire bundle before invoking target-writing commands.

The existing cryptography dual Apache-2.0/BSD license and existing test/runtime image
licenses continue to apply. No external dataset or backup service is added.
