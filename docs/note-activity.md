# Note and Daily Note activity

Refresh `/graph` and open **활동 열기**. NOTE captures NoteCreated/Updated/Retired; DAILY_NOTE captures DailyNoteChanged. A Daily Note body change intentionally appears in both streams: NOTE carries the body revision, DAILY_NOTE the immutable journal binding. Use the separate filters to browse either dimension. Note-to-Concept association events now have their own filter: see [Note Concept activity](note-concept-activity.md). Wiki-link/tag/property/attachment events remain separate future consumers.

AGENTS.md/PROJECT.md keep canonical Note bodies, Daily bindings, revisions and retained events in Content; Activity owns the durable Inbox and ClickHouse timeline. This increment follows those existing decisions and adds no AI, dependency, schema version, cross-owner SQL or canonical data migration.

NOTE pins the original title, state, actor, event ID, timestamp, trace, Note version and revision ID. It copies at most8192 UTF-8 bytes of the Markdown, ending at a whole code point, and exposes original body byte size (max32768) and truncation. A changed suffix beyond the excerpt still conflicts by full original Protobuf wire hash; deduplication never relies only on the excerpt. The frozen Note contract permits control characters other than NUL, and this reader preserves that compatibility. The browser renders plain escaped text, without Markdown, URL fetching or Wiki-link resolution. Full historical bodies remain in Content revision history.

DAILY_NOTE pins the literal journal date and IANA timezone, title, lifecycle and Note body version. Its event timestamp is save/change time. Neither current server timezone nor later timezone rules replace the stored date/zone. Ordinary Notes do not gain a journal binding. Reopening an unchanged Daily Note emits no new event, and archive retains the original binding and history.

Both kinds target only `/api/spaces/{spaceId}/notes/{noteId}`. Explicit current lookup checks the same Space/Note, strong bare version ETag and current authority, without touching sibling drafts. An archived current Note may return404 while activity remains. Filter/close/Space changes abort and discard pending reads; failed current reads clear current data, and revoked sessions clear private state. Existing date/kind/Space-bound cursors,20 default/100 max pages and no-store behavior remain.

Content's existing scoped HTTPS export now includes six original retained streams. Exact Read/Describe ACLs add only content.note.v1 and content.daily-note.v1 to the unchanged Activity group, for sixteen streams total. Original Protobuf v1 files, Registry versions, CDC connector/slot and event bytes stay unchanged. New V4 warmup changes only Activity readiness/seed flags, preserving every existing Inbox row and checkpoint. Legacy JSON without `note` reads as null. Recovery captures Kafka tails before all three owner scans; every scan must complete before seeding. Bounded per-owner STARTED/COMPLETED row-count logs help observe recovery without logging private bodies or service credentials.

The operator replay now reuses the existing Activity Hikari configuration: owner-only credentials, maximum3 connections, minimum1 idle,10s connection/statement limits and close-on-success/failure. It no longer opens a new physical PostgreSQL connection for every replayed event. The previous real three-owner replays took358/351 seconds for about29k Inbox rows; this is the evidence for improving connection reuse, not a throughput guarantee. Actual same-data preservation, connection limits and current replay timings are recorded after validation.
