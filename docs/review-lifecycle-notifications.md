# Feedback and grade retraction/restoration alerts

This increment extends the already-approved own-submission, per-Group opt-in in-app notifications to feedback and grade version retraction/restoration. Default-off reception, consent cutoff, membership epoch, author-only inbox and explicit read/archive/audit rules stay unchanged. No additional delivery channel or implicit publication of private learning progress. Original scores/opinions/retraction reasons remain exclusively in Collaboration; the inbox stores change kind and immutable source identifiers only.

Four added kind strings: FEEDBACK_RETRACTED, FEEDBACK_RESTORED, GRADE_RETRACTED, GRADE_RESTORED. Each is an immutable historical change fact, including reason corrections emitted by the original annotation aggregate. It never relabels a later review version or mutates an existing inbox item. Existing annotation no-ops emit no new source event. Exact original event SHA256 and source aggregate/version are retained for deduplication; annotations and original review aggregates are independent identities. Applying a restore before an earlier retraction is consumed cannot turn the retraction fact into a current state label.

Notification V4 adds only group_review_source_activation, with one persisted activation cutoff each for feedback-retraction and grade-retraction. The migration samples the database clock once. Existing users who previously enabled ordinary review alerts receive only newly supported changes occurring at/after this cutoff AND at/after their latest consent cutoff. Old annotations commit a durable BEFORE_SOURCE_ACTIVATION receipt, never an inbox item. Restarts/recovery do not advance the activation time. Missing activation configuration fails closed without committing a receipt or Kafka acknowledgement. The table is technical consumer configuration and remains outside CDC SELECT/publication.

The same consumer adds read-only literal topics collaboration.feedback-retraction.v1 and collaboration.grade-retraction.v1 to its existing three source subscriptions. Collaboration's dedicated bounded recovery export includes the same two source families, validates their immutable published envelopes/snapshots and returns only minimal metadata plus original envelope SHA256. No offset reset, consumer group replacement, slot/publication/PVC mutation or application Kafka producer. Every consumer still uses its own DB only. Original source Protos and notification.group-review.v1 remain byte-for-byte unchanged: change_kind is already a string, so the four supported values require no wire/schema rewrite. Existing V1 generated code preserves them. HTTP kind schemas and the web whitelist are extended together.

When opening an alert, the browser explicitly requests GET /api/groups/{groupId}/studies/{studyId}/assignments/{assignmentId}/submissions/{submissionId}/review-events/{eventId}. Collaboration first checks the existing fresh registered Space membership and author/current OWNER submission audience, then reads only its own retained immutable Outbox event by ID. Group/Space/Study/Assignment/Submission/author and event IDs must match. Returned metadata separates source aggregate/version (annotation revision), review ID/version (the exact opinion or grade revision), and submitted attempt. No answer, score, opinion, reason, file data or signed URL. Peer members cannot resolve it; current VIEWER authors can read their own source; removed authors are denied and current OWNER retains source review rights.

The UI validates the whole returned scope, source event/aggregate/version, kind and attempt before mounting the existing original submission component. It displays the exact historical target, e.g. 대상 채점 v1 · 채점 버전 철회, while the original component separately displays current grades and paged version history. A newer grade is not interpreted through an older marker. Opening never marks an alert read automatically. Failed/mismatched target reads clear source data and require explicit refresh. All state is memory-only and cleared/aborted on hidden/unmount/denial. Both current source and marker reads retain their existing authorization.

No new dependency or dataset. Existing service boundaries, asynchronous Outbox/Connect publication, current grading/annotation policies and Personal reminder subscriptions are preserved. The original target read uses the fixed-label brain.collaboration.submission.reads type notification-original; existing Notification delivery/failure/recovery counters and consumer readiness cover both additional source streams. No private content enters logs or metric labels.
