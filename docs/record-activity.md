# Private record activity

Current operational scope (2026-10-18): [Note Concept activity](note-concept-activity.md) extends the timeline to seventeen streams across Learning, Planning and Content. Use its current rollout/recovery instructions; the earlier increment and validation evidence below remain historical.

Bookmark, Question, Decision and their Concept associations now join the private Activity timeline. Creation, edits and retirement retain their original actor, event ID, time, trace and body version. Answer/outcome/rationale/alternatives and manual status are historical facts; later edits never overwrite them.

`RECORD_CONCEPTS` keeps the association ID/version distinct from the typed parent record ID/body version. Full ordered link snapshots preserve link and Concept IDs, including empty detach snapshots. Since the source contract contains no titles, historical link entries use a type label and never infer past names from current Knowledge data. Parent retirement adds its own source activity without inventing a link event.

Content is canonical. Activity owns only its durable PostgreSQL Inbox and derived ClickHouse timeline. The existing four frozen v1 Protobuf contracts and standard eleven envelope fields are unchanged. Exact read/describe topic ACLs extend the existing Activity consumer. The live consumer stages each validated event before committing the Kafka offset; byte conflicts and aggregate/version conflicts fail without acknowledgement. Duplicate/out-of-order events preserve history. Existing Learning/Planning entries and cursors remain compatible; `content` is null for old entries.

Content exposes `/internal/content/activity-events` with its own scoped service bearer and verified HTTPS. It reads only retained Content Outbox envelopes, five rows per page through a fixed event-ID watermark. It exports every original event, not the latest graph snapshots and not synthetic revision IDs. Cookie requests, duplicate parameters, non-GET/body-bearing requests and unknown queries are denied; Gateway has no internal export route. Do not delete retained Outbox rows until an equivalent immutable canonical event archive and recovery contract exist.

On a new Inbox or retention gap, Activity captures Kafka tail positions, scans Learning, Planning and Content, then consumes from those captured tails. All owner scans must succeed before seeding; reads stay unavailable during recovery. The additive V3 warmup preserves all existing rows and checkpoints. `python scripts/Rebuild-LocalActivity.py` safely replays retained canonical envelopes plus the existing Inbox without deleting either source or projection, recreating topics or resetting groups. Repeated ClickHouse inserts collapse by stable event ID using FINAL reads.

The existing private endpoint supports ALL and each of the four new kinds. Space authority is checked live for each read, including claimed guest Spaces; keyset cursors bind Space, kind, timezone and date range. OccurredAt is change time. Pagination stays 20 default/100 maximum; limits, HTTP budgets and low-cardinality event-kind metrics remain bounded. The browser renders historical facts as escaped text, never fetches a saved URL, resolves current owners only on explicit click, and never fills sibling drafts. Close/filter/Space changes invalidate pending responses; denial clears private state.

Local validation evidence is recorded in `docs/record-activity-validation.txt` and `.local/record-activity-proof.json` after deployment. Frontend visual redesign and new notification channels remain separate work.

## Local rollout and recovery

1. Run `python scripts/Provision-LocalActivity.py` to reuse credentials, add the Content-only export key and four exact read-only topic ACLs. No schema registration, connector reset or new Kafka group is needed.
2. Build/import/install Content first with the existing local image scripts, then Activity, then Gateway. Wait for each exact import Job on both nodes before installing. Both service and local Helm env lists contain the Content origin/key. Content's network policy admits only the existing Activity workload/rebuild labels in addition to its prior clients; the exporter separately requires its scoped bearer over verified HTTPS.
3. Activity V3 starts a complete three-owner canonical warmup. Allow it to finish before browser validation; a warmup503 indicates recovery, not an empty timeline. All retained histories are scanned, so an established local data set can take several minutes.
4. Run `python scripts/Rebuild-LocalActivity.py` for non-destructive operator recovery. The Job clones the deployed Activity image, carries only own DB/projector/public-trust and three export capabilities, has no HTTP Service selector and no canonical write capability. Wait for its exact Job to Complete and all Activity readiness checks to recover before inspecting the timeline. Failure deliberately leaves recovery visible; repair the dependency and rerun.
5. Validate using `Run-BackendValidation.py --content --content-kafka`, `--activity --activity-storage`, then the full backend suite. `Run-GraphWebValidation.py --record-activity-only` exercises the new UI; full `--public` includes real registered Space claims and all existing browser flows. See the validation evidence for exact completed Jobs and counts.
